# BASE.2 · Túnel y webhook de Meta con mensaje en bandeja — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Agregar el servicio `cloudflared` al compose como túnel saliente para los subdominios `crm.`
y `api.`, verificar automáticamente que el host no expone puertos entrantes, y dejar documentado si
el builder de automatizaciones de wacrm soporta condiciones por hora.

**Architecture:** Cloudflare Tunnel corre como un servicio Docker más dentro del compose (`tunnel`),
con rol `tunnel` según el contrato CT.2. El servicio abre una conexión saliente a la red de
Cloudflare; el host no abre ningún puerto. Las rutas internas son `crm.<dominio>` → `app:3000` y
`api.<dominio>` → `supabase-kong:8000`. El token del tunnel llega por `CLOUDFLARE_TUNNEL_TOKEN`
en `.env.local`. Una prueba de unidad sobre el compose verifica que el servicio `tunnel` no publica
puertos en el host (IT). La verificación end-to-end (mensaje en bandeja en < 5 s) y el registro del
webhook en Meta son pasos manuales de Juan.

**Tech Stack:** `cloudflare/cloudflared` (imagen Docker pineada), Docker Compose v2, TypeScript,
vitest.

**Spec:** `prd-hub` → `prds/wacrm-tenant-repo-template/slices/BASE.2-tunel-webhook-meta.md`
(orígenes: `03-alcance.md#compose-probado`, `03-alcance.md#fase-1`, `05-reglas.md#r1`,
`05-reglas.md#r4`).

## Review Focus

- **Token vacío o con espacios:** si `CLOUDFLARE_TUNNEL_TOKEN` está mal formado, `cloudflared run`
  falla en tiempo de arranque con un error de autenticación, no silenciosamente.
  → Tarea 2, test: `tunnelService.image` no contiene `:latest`.
- **Healthcheck falso positivo:** el healthcheck de `tunnel` debe confirmar conectividad real con
  la API de Cloudflare, no solo que el proceso arrancó.
  → Tarea 1, validar que el healthcheck usa `cloudflared tunnel info` o equivalente.
- **Puertos del host no chequeados después de añadir el servicio:** la prueba IT debe leer el
  compose parseado (no el YAML crudo) y verificar `publishedPorts` vacío en el servicio `tunnel`.
  → Tarea 2, test explícito.
- **`api.` apunta al puerto equivocado:** si el ingress de Supabase Kong no es 8000 en el momento
  de implementar (el puerto lo fija BASE.1), el webhook de Meta no llega al app.
  → La Tarea 1 documenta el puerto real del Kong en el comentario del YAML.
- **Servicio `tunnel` no declarado con `healthcheck: true` en el lector de CT.2:** si BASE.1
  construyó la topología sin leer el healthcheck del tunnel, `parseTopology` rechazará la entrada.
  → La Tarea 2, paso de verificación corre `parseTopology` completo.

- [ ] **Paso 3: Añadir el servicio `tunnel` a `docker-compose.yml`**

  Al final del bloque `services:`, antes del bloque `volumes:` si existe, añadir:

  ```yaml
    # Cloudflare Tunnel (outbound-only — no host ports required, satisfies R1).
    # Routes: crm.<DOMAIN> → http://app:3000, api.<DOMAIN> → http://supabase-kong:<KONG_PORT>
    # Set CLOUDFLARE_TUNNEL_TOKEN in .env.local (never commit the token).
    tunnel:
      image: cloudflare/cloudflared:<VERSION_PINEADA>
      command: tunnel --no-autoupdate run
      environment:
        TUNNEL_TOKEN: ${CLOUDFLARE_TUNNEL_TOKEN}
      depends_on:
        app:
          condition: service_healthy
        supabase-kong:
          condition: service_healthy
      restart: unless-stopped
      healthcheck:
        test: ['CMD', 'cloudflared', 'tunnel', 'info']
        interval: 30s
        timeout: 10s
        retries: 3
        start_period: 20s
  ```

  Reemplazar `<VERSION_PINEADA>` con la versión del paso 2 y `<KONG_PORT>` con el puerto real
  de Kong del paso 1. El servicio no declara `ports:` — eso es intencional (R1).

## Decisiones tomadas sin Juan

1. **Token del tunnel vía variable de entorno `TUNNEL_TOKEN`:** Cloudflare soporta pasar el
   token como variable de entorno al comando `cloudflared tunnel run`. Se eligió esta vía por
   consistencia con el resto de secrets en `.env.local`. La alternativa (montar un
   `config.yml` con la ruta del tunnel) se descartó por ser más compleja sin ventaja en esta
   fase.

2. **Healthcheck con `cloudflared tunnel info`:** Es el comando más liviano que confirma
   conectividad real con la API de Cloudflare sin necesitar `curl` ni dependencias extra en la
   imagen base de cloudflared.

3. **Rutas del tunnel (`crm.` y `api.`):** `crm.` va al app (puerto 3000) porque es la UI de
   wacrm; `api.` va a supabase-kong porque es el gateway de las APIs de Supabase que wacrm
   consume. El webhook de Meta puede llegar por `crm.` (la URL real la fija Juan al registrar
   el webhook) — si el fork usa una ruta bajo `/api/...` el webhook va igualmente por `crm.`
   (Next.js API routes). Ajustar en el `.env.local` de ser necesario.

4. **Imagen `cloudflare/cloudflared` con versión del día:** el implementador debe pinear la
   versión más reciente estable en el momento de implementar (paso 2 de la Tarea 1). Esta
   decisión delega la versión concreta al implementador porque el plan se escribe antes de que
   se ejecute, y una versión de 2024 sería obsoleta al correr en 2026.
