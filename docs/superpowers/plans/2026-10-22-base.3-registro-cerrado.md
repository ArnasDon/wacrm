# BASE.3 Registro cerrado — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bloquear el registro abierto en wacrm: `/signup` sin token de invitación redirige a `/login`; `/signup?invite=<token>` sigue funcionando.

**Architecture:** Regla nueva en `src/middleware.ts` (antes del bloque de auth-pages existente): si la petición llega a `/signup` sin el parámetro `invite`, redirige a `/login`. El bloque existente que ya redirige a `/dashboard` a un usuario autenticado que llega a `/signup` no cambia. La página `src/app/(auth)/signup/page.tsx` no se toca — ya lee el token y lo usa correctamente; el middleware es la única puerta.

**Tech Stack:** Next.js middleware (Edge Runtime), TypeScript, Vitest

## Decisiones tomadas sin Juan

- La restricción se implementa en el middleware (no en la página) para que el bloqueo ocurra antes de renderizar y no sea bypasseable vía JS deshabilitado.
- El redirect apunta a `/login` sin parámetros de error adicionales (coherente con cómo el middleware trata otros casos de acceso no autorizado en el mismo archivo).
- No se modifica la variable `DISABLE_SIGNUP` de Supabase Auth ni ninguna variable de entorno; el control es exclusivamente a nivel de ruta.

## Global Constraints

- Solo se modifica `src/middleware.ts` y `src/middleware.test.ts`. Ningún otro archivo.
- La PR solo toca `docs/superpowers/plans/` — el código lo implementa la PR de código posterior.
- Comandos de verificación: `npx vitest run src/middleware.test.ts` (dirigida) o `npm run lint && npm run typecheck && npm test` (completa).

## Review Focus

- `GET /signup?invite=` (valor vacío): debe redirigir igual que sin parámetro — el token vacío no es una invitación válida. → cubierto en Tarea 1, paso 1b.
- `GET /signup?invite=abc&otroParam=x`: el invite presente debe permitir pasar aunque haya otros query params. → cubierto en Tarea 1, paso 1c.
- Usuario ya autenticado en `GET /signup?invite=abc`: la regla del middleware existente lo redirige a `/join/<token>` — ese flujo NO debe romperse. → cubierto en Tarea 1, paso 1d (test de no regresión).
- `GET /signup` via POST u otro método: el config de `matcher` del middleware ya filtra solo GET; no hay riesgo aquí.
- Cookies de sesión rotadas en el redirect del registro bloqueado: deben propagarse igual que en el resto de redirects. → cubierto en Tarea 1, paso 1e.

- [ ] **Paso 3: Implementar la regla en `src/middleware.ts`**

Insertar el bloque siguiente **inmediatamente antes** de la línea que contiene el comentario `// Auth pages - redirect to dashboard if already logged in.` (aproximadamente línea 45 del archivo actual):

```typescript
  // Registro cerrado: /signup solo está disponible con token de invitación.
  // Sin él redirigimos a /login para que el usuario entre por invitación.
  if (
    !user &&
    request.nextUrl.pathname === '/signup' &&
    !request.nextUrl.searchParams.get('invite')
  ) {
    const url = request.nextUrl.clone()
    url.pathname = '/login'
    url.search = ''
    return withRefreshedCookies(NextResponse.redirect(url))
  }
```

La condición `!user` es necesaria: si el usuario ya está autenticado y llega a `/signup?invite=abc`, la regla del bloque `Auth pages` que le sigue lo llevará correctamente a `/join/abc`. Si llegara a `/signup` sin invite estando autenticado, lo mandaría a `/dashboard` (correcto también).
