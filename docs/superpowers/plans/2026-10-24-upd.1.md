# UPD.1 · Actualización del template por merge revisado como diff — plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** que un repo hijo baje los cambios de la plantilla por merge, los revise como diff antes de aplicarlos y que un chequeo falle si el cambio toca rutas de la empresa (CT.1) o rompe los nombres del compose (CT.2).

**Architecture:** un núcleo puro (`scripts/upd/revisar-cambio.ts`) que recibe la lista de archivos de un cambio (`git diff --name-status -z`) y, opcionalmente, el compose de antes y el de después, y devuelve un veredicto usando solo los helpers de los contratos (`esRutaDeEmpresa` de CT.1; `parseTopology`/`nameChanges` de CT.2). Una capa fina de git (`scripts/upd/git.ts`) arma esas entradas desde un rango (`base...head`) o desde un merge preparado y sin commitear (índice contra `HEAD`). Un CLI (`scripts/upd/revisar-cambio.cli.ts`, corrido con `tsx`) y un procedimiento (`scripts/upd/actualizar-desde-template.sh`) que hace `git merge --no-commit --no-ff`, muestra el diff, corre el chequeo y aborta si falla. Un workflow de CI corre el mismo CLI en las PRs de la plantilla y en las PRs `upd/*` de los hijos.

**Tech Stack:** TypeScript 6 (strict), zod 4, vitest 5, js-yaml 4, git, bash, `tsx` (nuevo, devDependency), Node 22.

**Spec:** `prd-hub` → `prds/wacrm-tenant-repo-template/slices/UPD.1-flujo-actualizacion.md`
(origen `03-alcance#actualizacion-template`, `05-reglas#r5`, `05-reglas#r8`; contratos que consume:
`slices/CT.1-contrato-config-empresa.md` → `contracts/cfg/tenant-config.ts`,
`slices/CT.2-contrato-servicios-compose.md` → `contracts/base/compose-services.ts`).

## Review Focus

1. **Renombres** (`R100 config/policies.yaml → config/old.yaml`, o un archivo del template movido a `config/`): se revisan **las dos** rutas, origen y destino; basta una de la empresa para bloquear (pinned en Tarea 1, prueba "renombre").
2. **Rutas con espacios, tildes o saltos de línea** en el diff: el parseo usa `git diff --name-status -z` (separado por NUL), no por líneas; `core.quotePath` no afecta (pinned en Tarea 1, prueba de `parsearNameStatus` con `config/políticas nuevas.yaml`).
3. **Merge con conflictos**: si `git merge --no-commit` deja rutas sin resolver, el chequeo corre igual sobre ellas (estado `U`), y si alguna es de la empresa el procedimiento aborta; si ninguna lo es, sale con código 2 y deja el merge para que la persona resuelva (pinned en Tarea 4, caso "conflicto en ruta de la empresa").
4. **Árbol sucio al arrancar**: el procedimiento se niega (código 3) si `git status --porcelain` no está vacío, para no mezclar cambios locales con el merge ni perderlos en el `--abort` (pinned en Tarea 4, caso "árbol sucio").
5. **Compose que renombra o quita un volumen** (`supabase-storage-data → storage-data`): los datos de la empresa quedarían en un volumen huérfano; se bloquea aunque el archivo `docker-compose.yml` sea del template (pinned en Tarea 1, prueba "volumen renombrado").

## Decisiones tomadas sin Juan

1. **Dos capas de chequeo, mismo código.** El slice pide "un chequeo que falla si un cambio de la plantilla toca rutas de la empresa". Se aplica (a) en la PR de la plantilla, contra `base...head`, para que la plantilla nunca traiga esas rutas, y (b) en el hijo, sobre el merge preparado, que es lo que garantiza R5 aunque (a) se haya saltado. Ambas usan `revisarCambio`.
2. **Merge, no rebase ni cherry-pick**, con `git merge --no-commit --no-ff <remoto>/<rama>` (por defecto `template/main`), sobre una rama `upd/<AAAA-MM-DD>` creada desde la rama actual. El procedimiento deja el merge preparado y sin commitear: la persona lee el diff, commitea y abre la PR `upd/*` en el hijo (R8). Nunca hace commit ni push.
3. **"Revisión como diff"** = el procedimiento imprime `git diff --cached --stat HEAD` y guarda el diff completo en `$TMPDIR/upd-<fecha>/cambio.diff` (directorio nuevo), y dice la ruta. La revisión real es la PR `upd/*` en GitHub.
4. **Si el chequeo falla, se aborta todo** (`git merge --abort`), no se "restauran" los archivos de la empresa y se sigue: restaurar en silencio ocultaría que la plantilla está rota, y R8 dice que nada se aplica solo.
5. **Compose (CT.2):** si el cambio toca `docker-compose.yml`, el compose propuesto tiene que pasar `parseTopology(toTopologyInput(doc, env))`; y `nameChanges(actual, propuestos)` bloquea cuando quita o renombra un servicio obligatorio o cualquier volumen. Agregar o quitar un servicio de `OPTIONAL_SERVICE_NAMES` solo se informa. `env` para `toTopologyInput` = las variables de `.env.example` del árbol propuesto (parseo `CLAVE=valor`, sin comillas), porque el chequeo no debe leer el `.env` real de la empresa.
6. **`tsx` como devDependency** para correr el CLI en TypeScript con los alias `@contracts/*` de `tsconfig.json` (Node solo no resuelve los alias). Es la única vez que se tocan los archivos calientes. Alternativas descartadas: `node --experimental-strip-types` (no resuelve `paths`) y correr el CLI dentro de vitest (frágil y raro).
7. **El workflow distingue plantilla de hijo por `github.repository`**: en `juancadavidc/wacrm-tenant-template` corre en toda PR a `main`; en cualquier otro repo (un hijo), solo en PRs cuya rama empieza por `upd/`. Así un hijo puede seguir cambiando su `config/` en PRs normales.
8. **La IT corre en `npm test`** (no detrás de una variable como `COMPOSE_IT`): solo necesita `git` y un temporal, tarda segundos y CI ya tiene git. Lleva `git config user.name/email` locales al repo temporal y `commit.gpgsign=false`.
9. **Códigos de salida del CLI y del procedimiento:** 0 = pasa; 1 = chequeo rechazado; 2 = merge con conflictos fuera de rutas de la empresa (queda para resolver a mano); 3 = árbol sucio o argumentos inválidos.
10. **El CLI se invoca con el `tsx` y el `tsconfig` del checkout que tiene el código** (`<raíz>/node_modules/.bin/tsx --tsconfig <raíz>/tsconfig.json`) y el repo revisado va en `--repo`; el `.sh` deriva `<raíz>` de su propia ubicación y pasa `--repo "$PWD"`. Así la IT corre sobre repos temporales sin `node_modules` ni `tsconfig` y sin red (revisión ronda 1).
11. **`nameChanges` se calcula siempre desde las claves crudas del compose propuesto**, antes de validar y aunque `toTopologyInput`/`parseTopology` lancen; el lanzamiento es un bloqueo más (revisión ronda 1).

Helpers locales del archivo de prueba (van después de los imports; agregar
`import type { ComposeTopologyInput } from '@contracts/base/compose-services';`). Construyen y
editan el documento crudo tal como lo devolvería `yaml.load`, con la forma que lee
`toTopologyInput` (`scripts/compose/topology.ts`): `services` y `volumes` como mapas por nombre;
`image` o `build: '.'` cuando el stub trae `image: null` (roles `app`/`cron`);
`healthcheck: { test: [...] }` para que salga `true`; `ports` en forma corta `host:container`;
montajes de volumen `nombre:/ruta` (el prefijo antes de `:` es el que cuenta como volumen nombrado).
Ninguno muta su entrada.

```ts
type DocCompose = {
  services: Record<string, Record<string, unknown>>;
  volumes: Record<string, Record<string, never>>;
};
type ServicioStub = {
  name: string;
  image: string | null;
  publishedPorts: { host: number; container: number }[];
  volumes: string[];
};
const HEALTHCHECK = { test: ['CMD', 'true'] };

function documentoDesde(input: ComposeTopologyInput): DocCompose {
  const services: DocCompose['services'] = {};
  for (const s of input.services as ServicioStub[]) {
    services[s.name] = {
      ...(s.image === null ? { build: '.' } : { image: s.image }),
      healthcheck: HEALTHCHECK,
      ports: s.publishedPorts.map((p) => `${p.host}:${p.container}`),
      volumes: s.volumes.map((v) => `${v}:/data/${v}`),
    };
  }
  const volumes: DocCompose['volumes'] = {};
  for (const v of input.volumes as { name: string }[]) volumes[v.name] = {};
  return { services, volumes };
}

// Renombra la clave en `volumes` y cada montaje `de:/…` de los servicios.
function renombrarVolumen(doc: DocCompose, de: string, a: string): DocCompose {
  const volumes = Object.fromEntries(
    Object.entries(doc.volumes).map(([k, v]) => [k === de ? a : k, v]),
  );
  const services = Object.fromEntries(
    Object.entries(doc.services).map(([n, s]) => [
      n,
      {
        ...s,
        volumes: ((s.volumes as string[]) ?? []).map((mnt) =>
          mnt.startsWith(`${de}:`) ? `${a}${mnt.slice(de.length)}` : mnt,
        ),
      },
    ]),
  );
  return { services, volumes };
}

function quitarServicio(doc: DocCompose, nombre: string): DocCompose {
  return {
    ...doc,
    services: Object.fromEntries(Object.entries(doc.services).filter(([n]) => n !== nombre)),
  };
}

function agregarServicio(doc: DocCompose, nombre: string, imagen: string): DocCompose {
  return {
    ...doc,
    services: {
      ...doc.services,
      [nombre]: { image: imagen, healthcheck: HEALTHCHECK, ports: [], volumes: [] },
    },
  };
}
```

Firmas del bloque **Produces**. Reglas:
- `parsearNameStatus`: tokens separados por `\0`; el estado es la primera letra del token (`R100` → `R`, `C075` → `C`); `R` y `C` consumen dos rutas (origen, destino).
- `revisarCambio`: una ruta es bloqueada si `esRutaDeEmpresa(ruta)` o `esRutaDeEmpresa(rutaOrigen)`; se reporta la que sea de la empresa. Compose solo si algún cambio tiene `ruta === 'docker-compose.yml'` y llega `compose` (si no, `compose: null`). `ok` = sin rutas de la empresa y sin bloqueos.
- Parte de compose, **en este orden y sin cortocircuito**: `nameChanges` se calcula **siempre** desde las claves crudas del documento (`Object.keys` de `services` y `volumes`), **antes** y con independencia de la validación; si `parseTopology`/`toTopologyInput` lanzan, eso suma un bloqueo y se sigue. Así un volumen renombrado a un nombre desconocido (que hace lanzar a `toTopologyInput`) igual aparece en `removedVolumes`.

  ```ts
  function revisarCompose(c: ComposeAntesDespues): { cambios: NameChanges; bloqueos: string[] } {
    const doc = (c.propuesto ?? {}) as {
      services?: Record<string, unknown> | null;
      volumes?: Record<string, unknown> | null;
    };
    // 1. Nombres crudos, siempre (no dependen de que el documento sea válido).
    const cambios = nameChanges(c.actual, {
      services: Object.keys(doc.services ?? {}),
      volumes: Object.keys(doc.volumes ?? {}),
    });
    const bloqueos: string[] = [];
    // 2. Validación contra CT.2; si lanza, un bloqueo y se sigue.
    try {
      parseTopology(toTopologyInput({ ...doc, services: doc.services ?? {} }, c.env));
    } catch (e) {
      bloqueos.push(`docker-compose.yml no pasa CT.2: ${e instanceof Error ? e.message : String(e)}`);
    }
    // 3. Quitas que bloquean (un renombre es quitar + agregar).
    for (const s of cambios.removedServices) {
      if (!(OPTIONAL_SERVICE_NAMES as readonly string[]).includes(s)) {
        bloqueos.push(`quita o renombra el servicio obligatorio "${s}"`);
      }
    }
    for (const v of cambios.removedVolumes) bloqueos.push(`quita o renombra el volumen "${v}"`);
    return { cambios, bloqueos };
  }
  ```

  `services: doc.services ?? {}` evita que `toTopologyInput` reviente con `Object.entries(undefined)` y lo convierte en un bloqueo de CT.2 normal (topología vacía).
- `formatearReporte`: primera línea `UPD · chequeo de actualización: OK` o `… RECHAZADO`; luego una línea por ruta de la empresa y por bloqueo del compose; luego los cambios informativos de `nameChanges`. Menciona R5 cuando hay rutas de la empresa.

```bash
raiz="$(cd "$(dirname "${BASH_SOURCE[0]}")/../.." && pwd)"
tsx="${UPD_TSX:-$raiz/node_modules/.bin/tsx}"
if [ ! -x "$tsx" ]; then
  echo "UPD: no encuentro tsx en $tsx; corre 'npm ci' en $raiz o define UPD_TSX" >&2
  exit 3
fi
chequeo() {
  "$tsx" --tsconfig "$raiz/tsconfig.json" "$raiz/scripts/upd/revisar-cambio.cli.ts" "$@" --repo "$PWD"
}
```

En un hijo real `raiz` = `$PWD` (el script vive en el hijo); en la IT `raiz` = el repo real y `$PWD` = el hijo temporal. En orden:
1. `git status --porcelain` no vacío → mensaje y `exit 3`.
2. `git fetch "${remoto}" "${rama}"`.
3. `git switch -c "upd/${UPD_FECHA}"`.
4. `git merge --no-commit --no-ff "${remoto}/${rama}"` (sin `-e`; un conflicto no corta el script: capturar el código).
5. Imprimir `git diff --cached --stat HEAD`; crear `dir=$(mktemp -d "${TMPDIR:-/tmp}/upd-XXXXXX")` y guardar `git diff --cached HEAD > "$dir/cambio.diff"`; imprimir la ruta.
6. Correr `chequeo --merge` capturando el código (`set +e; chequeo --merge; codigo=$?; set -e`).
7. Código 1 → `git merge --abort`, volver a la rama de partida, borrar `upd/<fecha>`, `exit 1`. Código 2 → mensaje "resuelve los conflictos y commitea", `exit 2`. Código 0 → mensaje "revisa el diff, commitea y abre la PR upd/*"; `exit 0`. **Nunca** `git commit` ni `git push`.
