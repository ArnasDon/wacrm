# VIS.1 · Visibilidad por asesor en bandeja, búsqueda y URL directa — plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** el módulo `visibilidad` (I3): con el módulo encendido, un asesor solo ve en la bandeja, el contador de no leídos y la búsqueda las conversaciones asignadas a él; la URL directa de un chat ajeno muestra "sin acceso"; admin y owner ven todas y filtran por asesor y por "sin asignar". Todo pasa por una sola función compartida, `visibleConversations(usuario)`.

**Architecture:** el ocultamiento es solo de interfaz (R27): los datos siguen llegando por RLS como en wacrm y se filtran en el cliente con una función pura (`src/modulos/visibilidad/visibilidad.ts`). El servidor sabe si el módulo está encendido por el registro de MOD.1 (`obtenerFlujoEntrada().cargados`); el layout del dashboard lo lee en cada request y se lo pasa a un contexto de cliente (`VisibilidadProvider`). La bandeja deriva su lista visible en un solo punto (la página), así la búsqueda y los filtros existentes operan sobre lo visible; el contador del sidebar usa la misma función. Apagado, todo se comporta como wacrm (R16).

**Tech Stack:** Next 16 (App Router), React 19, TypeScript estricto, zod 4, vitest (entorno `node`, `renderToStaticMarkup` para componentes), next-intl.

**Spec:** prd-hub `prds/wacrm-tenant-repo-template/slices/VIS.1-visibilidad-bandeja.md`; `03-alcance.md#modulo-visibilidad`; reglas R26, R27, R29 (`05-reglas.md`); contrato consumido `prds/wacrm-tenant-repo-template/slices/CT.3-contrato-modulos.md` (en este repo: `contracts/mod/module.ts`, plan `docs/superpowers/plans/2026-10-24-ct.3.md`).

## Review Focus

1. **Rol aún sin resolver (`accountRole === null`) con el módulo encendido:** la bandeja no debe mostrar todas las conversaciones ni un segundo; falla cerrado (lista vacía, `listo: false`) hasta saber el rol (Tarea 1, "sin rol resuelto no ve nada").
2. **Conversación reasignada a otro asesor mientras el asesor la tiene abierta (evento realtime):** desaparece de la lista y el panel pasa a "sin acceso" sin recargar (Tarea 1, `puedeVer` tras el cambio; Tarea 4, la página deriva el acceso del estado, no de un efecto).
3. **Enlace directo de un asesor sin ninguna conversación visible (lista vacía):** igual muestra "sin acceso"; hoy wacrm ignora el enlace si la lista está vacía (Tarea 1, `resolverEnlaceDirecto` con lista vacía).
4. **Conversación nueva (INSERT realtime) de otro asesor o sin asignar:** no aparece al asesor ni suma al contador (Tarea 1, `contarNoLeidas` con filas ajenas y sin asignar).
5. **Config encendida en una imagen construida sin `config/`:** el layout no puede quedar prerenderizado con el módulo apagado; se lee en cada request (Tarea 3, `connection()` en el layout y prueba de `estadoVisibilidad`).

## Decisiones tomadas sin Juan

1. **Firma de la función compartida:** `visibleConversations(usuario)` (nombre literal de R27) recibe `{ userId, rol, moduloActivo }` y devuelve un objeto `Visibilidad` con `listo`, `veTodas`, `puedeVer(c)` y `filtrar(lista)`. Un solo lugar decide; VIS.2 la reutiliza para ficha, embudo, dashboard y notificaciones.
2. **Viewer se trata como asesor** (solo ve lo asignado a él, en la práctica nada): R26 solo da "ver todas" a admin y owner; ante la duda, mínimo privilegio. Agent y viewer restringidos; owner y admin ven todas.
3. **Config vacía:** `ConfigVisibilidadSchema = z.strictObject({})`. Los roles que ven todo los fija R26, no la empresa; el `rolesVenTodo` de la CDC de CT.3 era ilustrativo (decisión 9 de CT.3). La CDC de CT.3 sigue pasando porque usa su propio esquema.
4. **Rol sin resolver con el módulo encendido = no ve nada** (`listo: false`) y la página no monta la lista ni resuelve el enlace directo hasta `listo`. Así nunca se pinta la bandeja completa a un asesor ni se marca "sin acceso" por error.
5. **"Redirige o muestra 'sin acceso'" → se muestra** un panel "Sin acceso" en el lugar del chat, con botón para volver a `/inbox`. Mismo panel si el id no existe o es de otro asesor (no revela si existe). Apagado, el enlace se comporta como wacrm.
6. **La lista visible se deriva en un solo punto** (la página: `vis.filtrar(conversations)`), no en cada `setConversations` (realtime, hidratación, recarga). El estado sigue guardando lo que da RLS; la búsqueda, los filtros de wacrm y los de contacto corren sobre lo visible. Un chat que deja de ser visible (reasignado) se detecta en el render, no con un efecto (regla `react-hooks/set-state-in-effect`).
7. **Filtro por asesor:** select nativo (Todos / Sin asignar / cada miembro con rol `agent` de `fetchAccountMembers`), solo para quien `veTodas` con el módulo encendido. "Sin asignar" = `assigned_agent_id` vacío **en cualquier estado** (R29); el filtro `unassigned` de wacrm (solo abiertas) se deja tal cual. El filtro no va en la URL (YAGNI).
8. **El servidor lee el estado en cada request:** el layout llama `await connection()` (Next 16) antes de `estadoVisibilidad()`, para que el build (sin `config/`) no lo prerenderice apagado.
9. **API pública `api/v1/conversations` no se filtra:** usa API keys de la cuenta, no es interfaz de asesor; R27 limita el ocultamiento a la interfaz.
10. **Carpeta `src/modulos/visibilidad/`**, junto al registro de MOD.1 (`src/modulos/`). El plan de ASG.1 usa `src/modules/asignacion/`; ver "Para confirmar".
11. **Dos PRs** (Parte 1: 8 archivos; Parte 2: 15), porque el total pasa de 15.
12. **`servidor.ts` sin el paquete `server-only`:** no está en `package.json` y agregarlo tocaría archivos calientes; se sigue la convención de `src/lib/auth/account.ts` (comentario de cabecera "solo servidor" y frontera natural por las APIs de Node/`next/headers`). Así `vitest` puede importar `servidor.ts` en la CDC.

**Para confirmar con Juan:** (a) viewer restringido como asesor (decisión 2); (b) "sin acceso" en vez de redirigir (decisión 5); (c) carpetas de módulos: MOD.1 usa `src/modulos/` y ASG.1 `src/modules/asignacion/`; VIS sigue a MOD.1 y conviene alinear ASG.1 al implementarlo.
